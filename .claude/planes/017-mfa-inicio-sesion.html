PLAN 017

MFA en el inicio de sesión (TOTP + código por correo + passkeys)

corporate-app · corporate-api · corporate-front · Estado: aprobado · 2026-10-01

Contexto

Hoy el login es de un solo factor. Al crear un usuario se le asigna la contraseña por defecto del secret, que es compartida entre todas las cuentas nuevas, y se marca must_change_password=1. Con esa marca, el plan 015 bloquea la API con un 403 password_change_required hasta que el usuario cambie la contraseña; solo deja pasar /auth/me, /auth/menu y /auth/change-password. Este plan aprovecha ese primer ingreso obligatorio para enrolar un segundo factor, y desde ahí lo exige en cada login.

Decisiones del usuario

  • Se implementan TOTP, código por correo y passkeys; SMS queda fuera.
  • MFA es obligatorio para todos a través de MFA_REQUIRED; en dev queda en false.
  • En el primer ingreso se pide un código al correo antes de cambiar la contraseña. Como la contraseña por defecto es compartida, conocerla no basta: el código prueba que quien entra controla el correo del colaborador.

Restricción de las passkeys

WebAuthn solo funciona si el RP ID es un nombre de dominio. No acepta direcciones IP (la única excepción es localhost), y los navegadores lo desactivan cuando el certificado TLS da error. Hoy el front se publica en https://${ALLOCATED_IP}:puerto, por lo que las passkeys dependen de dos variables, WEBAUTHN_RP_ID y WEBAUTHN_ORIGINS:

  • Mientras no estén configuradas, la API no ofrece el método y el front oculta la opción. TOTP y correo funcionan igual sobre la IP.
  • Para activarlas en test/prod se necesita un nombre DNS interno que apunte a ALLOCATED_IP y un certificado para ese nombre, emitido por una CA en la que confíen los equipos. Este punto se relaciona con el plan 000.
  • En dev se prueban con https://localhost.

Flujo

Primer ingreso (must_change_password=1):
  POST /auth/login (pwd temporal) → sesión pre-auth {stage:"EMAIL_VERIFY"} → 200 {next:"EMAIL_VERIFY"}
  POST /auth/mfa/email/send   → código de 6 dígitos al correo de la persona
  POST /auth/mfa/email/verify → pasa a la marca mustChangePassword (flujo del plan 015 intacto)
  PATCH /auth/change-password → invalida sesiones → re-login
Login sin ningún factor enrolado (y MFA_REQUIRED):
  login → sesión completa con marca mfaEnrollmentRequired
        → 403 "mfa_enrollment_required" salvo /auth/me, /auth/menu, /auth/mfa/enroll/*
  enrolar passkey | app TOTP | correo → 10 códigos de recuperación (una sola vez) → re-login
Login normal:
  login → sesión pre-auth {stage:"MFA"} (sin req.session.user) → 200 {next:"MFA", methods:[...]}
  passkey: POST /auth/mfa/webauthn/options → navigator.credentials.get → POST /auth/mfa/webauthn/verify
  totp / email / recovery: POST /auth/mfa/verify {method, code}
  → recién ahí session.user (regenerate) / tokens si issueTokens

Regla clave: mientras el usuario no pasa el segundo factor, no existe req.session.user y no se emiten JWT. De esta forma authenticate, Socket.io y cualquier ruta nueva quedan cerradas por defecto. Un usuario puede tener varios factores enrolados y, al iniciar sesión, usa el que prefiera.

Cambios en corporate-api

  1. Esquema MSSQL en migrate.ts, con el guard IF NOT EXISTS sys.columns:
    • users: columnas nuevas mfa_totp_secret_enc, mfa_email_enabled y mfa_enrolled_at.
    • user_webauthn_credentials: credential_id único, public_key, sign_count, transports, device_name, aaguid, backed_up y last_used_at.
    • user_mfa_recovery_codes: el código hasheado con bcrypt y used_at.
  2. Librería library/mfa/:
    • totp.ts, con node:crypto y sin dependencias nuevas.
    • secretBox.ts, cifrado AES-256-GCM con la clave guardada en un secret.
    • recoveryCodes.ts.
    • webauthn.ts, sobre @simplewebauthn/server.
  3. Redis:
    • Código de correo hasheado, con TTL de 5 min y una espera mínima entre reenvíos.
    • Contador de intentos: al quinto fallo se destruye la sesión pre-auth.
    • Protección contra reutilización de un código TOTP ya usado.
    • Secreto TOTP pendiente mientras dura el enrolamiento.
    • Challenge WebAuthn de un solo uso.
  4. Sesión: estado mfaPending, válido 10 min, y la marca mfaEnrollmentRequired.
  5. auth.controller:
    • login decide en qué etapa queda el usuario.
    • completeLogin() se comparte entre login y la verificación MFA.
    • refresh conserva la marca de enrolamiento pendiente.
  6. mfa.controller y rutas /auth/mfa/*:
    • Cubre la etapa pre-auth, el enrolamiento y la administración de los propios factores.
    • Borrar un factor o regenerar los códigos exige haber verificado un factor recientemente, y el usuario nunca puede quedar con cero factores.
    • Cada ruta tiene su propio rate limiter.
  7. authenticate:
    • Nuevo 403 mfa_enrollment_required.
    • Nuevo middleware authenticateAllowingPending.
    • Nuevo motivo de invalidación mfa_reset.
  8. Admin: PATCH /users/:id/mfa/reset, protegido con users:update.
  9. Correo: sendMfaCodeEmail(). Si el envío falla, la API responde 503. El código nunca se registra en los logs.
  10. Socket.io: rechaza las sesiones que tengan el enrolamiento pendiente.
  11. Env/secrets:
    • Variables nuevas: MFA_REQUIRED, MFA_ENCRYPTION_KEY_FILE, WEBAUTHN_RP_ID y WEBAUTHN_ORIGINS.
    • ensure-backend-secrets.ps1 genera la clave de cifrado.

Cambios en corporate-front

  • AuthContext incorpora los pasos nuevos y usa @simplewebauthn/browser.
  • Pantallas nuevas:
    • EmailVerifyPage.
    • MfaVerifyPage.
    • MfaEnrollPage, con el QR generado localmente con qrcode.
    • «Seguridad de mi cuenta».
  • AppRoutes: el gate redirige a /mfa/enroll.
  • Botón de administración «Restablecer MFA».
  • nginx: se agrega publickey-credentials-get/create=(self) a la cabecera Permissions-Policy.

Verificación

  • Pruebas unitarias:
    • TOTP contra los vectores de la RFC 6238.
    • secretBox.
    • Códigos de recuperación.
    • webauthn: challenge reutilizado, origen incorrecto y sign_count.
  • Pruebas de integración:
    • No hay session.user antes del segundo factor.
    • Bloqueo tras 5 intentos fallidos.
    • Rechazo de un código TOTP ya usado.
    • Primer ingreso sin verificar el correo.
    • 403 mientras falta el enrolamiento.
    • issueTokens.
    • Reset desde administración.
    • Passkeys deshabilitadas cuando no hay RP ID.
    • No se puede borrar el último factor.
  • Pruebas manuales:
    • En dev, sobre https://localhost.
    • En Testing, TOTP y correo.
  • /security-review antes de pasar a master.

Pendiente fuera del código

Para activar las passkeys en test/prod hay que definir el nombre DNS interno y conseguir un certificado de confianza. Las passkeys quedan atadas a ese dominio: si el dominio cambia, los usuarios tienen que volver a enrolarlas.
